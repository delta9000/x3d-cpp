## Findings

- **TXF-2** [major/OPEN] — §18.4.8: The CPU reference host implements all TextureCoordinateGenerator modes; the OpenGL PoC still implements a subset.
  - CPU unlit, Phong and PBR select coordinates independently for each texture stage and material slot. All eleven Table 18.6 modes consume local/eye positions and normals, noise scale/translation and refraction parameters; generated coordinates receive the matching TextureTransform. Deterministic 3D Perlin noise and refract-based mapping are documented implementation choices where the published table is underspecified. Tests: texcoord_gen_test and interchange_test. The PoC still handles four camera-space modes per vertex, has the reversed reflection eye vector, and maps the other modes to authored UVs. This finding remains open for that consumer. (2026-10-02)
- **REQ-MULTITEXTURE** [major/OPEN] — §18.2.4; 18.4.3-18.4.5: The CPU reference host combines all MultiTexture modes with independent stage coordinates; the OpenGL PoC still binds only the first matching slot.
  - CPU implements all Table 18.3 modes, separate RGB/alpha mode tokens, Table 18.4 source selection of Arg2, and Table 18.5 post-operation functions. Each stage selects its MultiTextureCoordinate channel or named mapping and matching MultiTextureTransform, including generators. A single TextureTransform applies to every channel. Live transform and nested coordinate edits refresh baked meshes and coordinate-generation descriptors through the existing dependency indices; RuntimeSession regressions cover both channels. Tests: multi_texture_test and interchange_test, including rendering two stages with distinct transformed UVs and a material-free Appearance. The published table contradicts itself for REPLACE and SELECTARG2: REPLACE selects the stage texture (Arg1), SELECTARG2 selects the previous result (Arg2), following the respective operation meanings. The OpenGL PoC has no stage combiner; this finding remains open for it. Annex B explicitly includes MultiTexture despite its component level exceeding Texturing 2; the conformance view and CLI preserve that node-table exception. (2026-10-02)
- **TDN-5** [major/CLOSED] — §8.2.4.1, 16.4.2, 18.4.2: AudioClip/MovieTexture have no time-lifecycle System — startTime/loop/isActive inert.
  - MediaTimeSystem (attached by attachStandardRuntime) runs the shared X3DTimeDependentSystem lifecycle for AudioClip, MovieTexture and BufferAudioSource: enabled, loop, and a cycle of duration_changed / pitch (AudioClip), / speed (MovieTexture), or buffer seconds over playbackRate x detune (BufferAudioSource); an unknown duration plays until stopTime (media_time_test, sound_immersive_test). Decoding and playback remain separate (SND-4).
- **ENC-VRML-SFIMAGE** [major/FIXED `1e3c51d`] — §ISO 19776-2 5.3 (sfimageValue): ClassicVRML SFImage READER consumes only width and discards height/components/all pixel words — a 2x2 texture parses back as `2 0 0` (empty).
  - Real scenes NetworkedCamera.x3d, examples/.../textured_text.x3d: `image='2 2 3 0 65280 255 16711680'` survives XML->JSON direct, the .x3dv even WRITES it correctly, but reading that .x3dv back yields `[2,0,0]` — every inline PixelTexture destroyed the instant the scene passes through ClassicVRML. Fix: the ClassicVRML SFImage parser must consume width*height pixel words after the `w h comp` header. (round-trip sweep, newly surfaced.) CLOSE: NodeBuilder::collectFieldValue special-cases SFImage (3 header tokens then w*h pixel words; hostile headers capped at 2^20 per axis). Regression: codec_string_hardening_test (SFImage operator== across the .x3dv hop).
- **VIS-SPHERE-NOUV** [major/FIXED] — §13.3.6, 18.4.10: Sphere with an ImageTexture (and NO Material) rendered untextured (flat white) — Geometry/Sphere/texture.x3d. FIXED: the VTS decal now applies (upright, vertically centred per the scene description).
  - Mischaracterized originally: the sphere DOES carry texcoords (tessellateSphere emits them). The real cause is the no-Material case — an Appearance with an ImageTexture but no Material is unlit per spec (§12.2.5), so the extractor correctly surfaces MaterialModel::Unlit with the image on the EMISSIVE slot (MaterialSystem.hpp). The PoC's UNLIT shader had no texcoord/sampler at all, so the texture was never sampled (Box/texture.x3d has a <Material/> -> Phong path, which is why it worked). Fixed PoC-side: added aTexCoord + sampler2D to unlit.vert/unlit.frag and bound the {Emissive,BaseColor,Diffuse} slot in the unlit draw path. SDK extraction was already spec-correct.
- **VIS-MOVIE-DECODE** [major/FIXED] — §23.4.1: MovieTexture frames were never decoded — TextureRef::Source::Movie was surfaced but no consumer decode path existed, so movie-textured scenes rendered the white/last fallback (blank). FIXED for MPEG-1: the MovieDecoder seam + pl_mpeg Backend A play the video onto geometry (the whole NIST corpus is MPEG-1).
  - Implemented per ADR-0041: the MovieDecoder seam (runtime/extract/MovieDecoder.hpp) + Backend A pl_mpeg (runtime/io/plmpeg/, flag-gated x3d_plmpeg) wired into the PoC, which decodes the current media-time frame and uploads it as the texture each tick. The NIST .mpg files are RAW elementary video streams (no MPEG-PS system layer), so the backend drives pl_mpeg's low-level plm_video_t directly for those (plm_t + seek for program streams). Verified by the x3d_movie_tests semantics-contract test and by rendering Appearance/Appearance/movietexture.x3d (the VTS card plays on box/sphere/cone/cylinder). Theora since shipped as MovieDecoder Backend B (TheoraMovieDecoder, seam-status.md — the seam is STABLE); WebM remains a follow-up. MovieTexture time-lifecycle nuance tracked by TDN-5.

- **TXF-4** [minor/FIXED] — §18.4.9: CPU reference sampler honored only repeat/clamp — MIRRORED_REPEAT and CLAMP_TO_BOUNDARY were ignored and the magnification filter was not applied.
  - CPU Texture.hpp consumes all extracted boundary modes and borderColor, magnification and minification filters, generateMipMaps and anisotropy (supported maximum 16). Generated box-filter mip levels use nearest/bilinear selection and nearest/trilinear mip selection; absent mipmaps fall back to the corresponding base-level filter. Derivatives are perspective-correct per UV channel and are recomputed for procedural coordinates. Tests: texture_render_test and interchange_test. Scope is the CPU reference sampler, not the OpenGL PoC. (2026-10-02)
- **TXF-1** [minor/CLOSED] — §18.4.10: TextureTransform matrix application order divergence (translate/center/rotate/scale/−center) — UVs transformed incorrectly for non-trivial transforms.
  - Order fixed to the normative matrix Tc' = C·S·R·C⁻¹·T·Tc (right-to-left: translate → pivot → ROTATE → SCALE → un-pivot), matching §18.4.10's '(in order)' list — rotation BEFORE scaling. The contradicting prose sentence ('rotation ... after the scaling operation has been applied') is treated as an editorial error. applyTextureTransform + makeTextureTransform3x3 (TextureTransform2D.hpp) now agree; the centre pivot convention is unchanged. Regression: texture_extract_test (testTextureTransformOrder: π/2 about centre (0.5,0.5) + scale (2,3) + translation → (0.1,0.05), plus a make3x3 cross-check). (2026-06-27)
